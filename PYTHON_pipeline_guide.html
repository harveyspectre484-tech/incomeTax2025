canonicalize_legal_json.py

canonicalize_legal_json.py

Turn section JSON into canonical legal units

Converts nested, structured section JSON into a consistent collection of individually identified legal provisions and their relationships. This is the first requested script in the data preparation workflow.

Inputs

  • A single structured section JSON file, or a directory containing *section.json, commonly txt_to_json/.
  • chapter.md for Chapter / Division / Subdivision placement; reviewed reference_overrides.json when available.
  • Optional Act name and jurisdiction; defaults are Income-tax Act, 2025 and India.

Outputs

  • Directory mode: canonicalize_legal_json/<number>section_can.json for each input file, plus canonicalize_legal_json/chapter_hierarchy.json.
  • Each section result contains section_number, hierarchy_path, legal_units, external_nodes and graph_edges. The chapter file contains hierarchy_nodes and graph_edges.
  • Single-file mode: one JSON file at the supplied output path; it does not also write a standalone chapter_hierarchy.json.
  • Console: number of section files / hierarchy nodes or number of canonical units written.
How it works, when to use it, and example

What the code does

  • Walks sections, subsections, clauses, items, attached blocks and tables; separates a unit’s own text from the richer retrieval_text used for searching.
  • Builds canonical IDs, human-readable citations, explicit parent_id values, source coordinates, and parent / contains edges. Some units are derived from inline clauses or repaired longline structures.
  • Linearizes table rows and creates independently addressable complex cell items. Extracts internal, Schedule and external references, including contextual references and ranges; applies reviewed overrides.
  • Loads the chapter catalog and discovers external Act identities and aliases. External nodes are placeholders for references, rather than imported external statutory text.

Usage notes

  • This script handles sections. Canonical Schedule files must be prepared separately by canonicalize_schedule_json.py, which is outside the requested inventory.
  • Directory output filenames follow input filenames. Rebuilding an individual section alone does not refresh downstream graph and search files.

Next → Supply the canonical section directory, chapter_hierarchy.json and canonical Schedule directory to collect_graph_nodes.py.

Example use

python3 canonicalize_legal_json.py txt_to_json canonicalize_legal_json \
  --chapter-file chapter.md --reference-overrides reference_overrides.json

collect_graph_nodes.py

Collect a common node record for every legal unit

Combines canonical sections, chapter hierarchy and Schedules into one candidate node file while preserving canonical IDs.

Inputs

  • canonicalize_legal_json/*section_can.json.
  • canonicalize_legal_json/chapter_hierarchy.json (or --hierarchy-file).
  • canonicalize_schedule_json/schedule*_can.json.

Outputs

  • candidate_graph_nodes.jsonl: one candidate node object per line.
  • candidate_graph_nodes_summary.json: counts, type inventory, duplicate IDs and mapping findings.
  • candidate_graph_nodes_report.csv: field coverage and mapping / provenance issues.
  • All three locations are supplied on the command line; the example uses graph_data/.
How it works, when to use it, and example

What the code does

  • Maps legal_units to shared graph fields such as id, node_type, citation, parent_id, text, retrieval_text, hierarchy, jurisdiction and provenance.
  • Maps hierarchy_nodes from the chapter catalog and retains additional unit fields in source_properties.
  • Inventories node types and field coverage; reports missing required fields, hierarchy / coordinate issues and repeated IDs. Keeps candidate occurrences unmerged.
  • Counts section external-node occurrences as deferred and excludes those placeholders from candidates.

Usage notes

  • Repeated IDs are reported for the later identity check; collection does not choose a winning record.
  • Read required_mapping_issue_count and hierarchy_source_issue_count in the summary. The script does not turn these findings into a failing exit status.

Next → The candidate ID catalog is needed by collect_graph_edges.py.

collect_graph_edges.py

Collect and classify graph relationships

Reads existing canonical relationships and separates verified relationships from records that still need resolution.

Inputs

  • Candidate node JSONL from collect_graph_nodes.py.
  • The same canonical section, Schedule and chapter files used for node collection.

Outputs

  • resolved_graph_edges.jsonl: resolved edge occurrences before deduplication.
  • pending_graph_edges.jsonl: unresolved, ambiguous, deferred-external or invalid occurrences.
  • graph_edges_summary.json: source / resolved / pending counts and classification reasons.
  • graph_edges_report.csv: pending or invalid records and their reasons. Paths are supplied by flags.
How it works, when to use it, and example

What the code does

  • Normalizes from_id, to_id, edge_type, reference_text, resolution metadata, source file and extra source_properties.
  • Resolves a permitted internal edge only when both endpoint IDs each occur exactly once in the candidate catalog.
  • Keeps missing / ambiguous endpoints, external targets, malformed records and unknown types in the pending output with appropriate status and report entries.
  • Preserves parent, contains, references, references_schedule and annotates relationships; external reference types are retained for audit.

Usage notes

  • It collects reference edges already present in canonical JSON; reference extraction happens earlier.
  • An endpoint check confirms graph membership, not the legal correctness of a reference. Invalid counts must be inspected; this collector does not explicitly exit with a failure status for them.

graph_data/deduplicate_graph_records.py

Produce the final active and pending graph files

Applies node identity and relationship duplicate rules so downstream tools receive one accepted node per canonical ID.

Inputs

  • Candidate nodes, resolved edge occurrences and pending edge occurrences from the collectors.

Outputs

  • graph_nodes.jsonl: accepted active nodes; graph_edges.jsonl: deduplicated active edges.
  • graph_pending_edges.jsonl: deduplicated pending records, including edges moved because of conflicts.
  • graph_node_conflicts.jsonl: conflicting node occurrences.
  • graph_identity_report.csv and graph_identity_summary.json: merge decisions and totals. All are written under --output-dir.
How it works, when to use it, and example

What the code does

  • Groups nodes by full canonical ID and compares normalized identity / content while excluding provenance and source-position differences.
  • Merges matching occurrences and their provenance. Places all conflicting occurrences in a conflict file rather than selecting one.
  • Moves resolved edges touching conflicting IDs to pending with ambiguous status.
  • Merges equivalent edges while retaining material differences such as range position, Schedule locator and override metadata.

Usage notes

  • Exits with code 1 if blocking node conflicts remain, after writing the outputs.
  • Pending edges are not automatically promoted to active relationships. Changes to source identity require rebuilding the earlier stages.
